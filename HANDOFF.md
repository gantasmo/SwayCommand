# SwayCommand handoff

Internal engineering note for the next engineer or agent. It is deliberately **not** in `docs/`, not in the documentation index, and not packaged, `electron-builder.yml` ships `docs/**/*.md` and `README.md` by exact name, so a root-level file never reaches an end user. Product documentation lives in [`docs/`](docs/); start with [docs/OVERVIEW.md](docs/OVERVIEW.md) for terminology. Last revised 2026-08-21, after the fifth pass.

**How this note stays short.** Delivered work waits for the user's approval inside `<!-- prune:<id> -->` ... `<!-- /prune:<id> -->` blocks in §2, one block per task, most recent last. When the user approves a task, run `node scripts/handoff-prune.js <id>` (`--list` prints the ids, `--all` clears them) and the block goes; its id lands on the ledger line at the end, and git history keeps the detail. Everything outside the blocks is the durable core (state, standing rules, how to verify, known gaps, packaging) and is edited in place, never appended to.

### boot-warm, the first-launch lag, measured and fixed (fifth pass, 2026-08-21)

The user: "when the app first loads it is really REALLY laggy." Two false starts are worth recording: `stats.worst` measured from the clamped `dt` can only ever read 50, it now reads the raw delta, and the lag does not reproduce on a warm shader cache at all; a fresh `--user-data-dir` per run is how it was made to show. Then a boot timeline: `createEngine` blocked for 1,018 ms, of which **982 ms was the PMREM RoomEnvironment**, built on every launch for the three chrome scenes that use it; and the old one-scene-per-frame warm did build + synchronous `renderer.compile` + first draw in one frame each. Built: the environment is a lazy getter on the creation context (built on first need, inside the warm pipeline); the warm pipeline is four stages one frame apart, build, `compileAsync` **with the half-float warm target bound**, async link (`KHR_parallel_shader_compile`, a 6 s guard), one 32 px draw, and only then is a scene `ready`; a cut or fade to a cold scene is deferred until it is (the stage holds what it shows, a fade holds at zero, Auto-VJ never picks while a switch is pending, `currentScene` names the pending scene); the pipeline stands down on a frame past 28 ms except when the stage waits on that scene; the boot door shows `Warming visuals · n of m` and waits for the warm (6 s at most) before opening by itself; the doctor reads the GPU name off the stage's own context (it opened a second WebGL2 context just to ask, and got "WebKit WebGL"). Binding the warm target during the async compile was the decisive find, the D3D driver compiles a program for the target signature it first meets, and linking against the canvas then drawing into half-float cost a second, synchronous compile on first draw: 167 / 383 / 968 / 550 ms for warp / vjshader / mandelbulb / valley on a cold cache; bound, 5 / 6 / 5 / 20 ms. Cold-cache boot on this machine: time to an interactive project 1,477 -> 557 ms; cumulative main-thread stall in the first seven seconds ~5 s -> ~1.9 s, the largest remaining piece the 870 ms PMREM build when a chrome scene warms; warm-cache boot worst frame 133 to 167 ms, behind the door. `stats` gained `worst`, `slow`, `stallLog`, `warm[id] = { buildMs, submitMs, linkMs, drawMs }`; the engine gained `sceneReady`, `warmProgress`, `gpuName`. Docs: ENGINE ("The warm pipeline", Stats), ENVIRONMENT (probe), TROUBLESHOOTING ("First launch after an install stutters").

## 3. Standing rules

- **Pads are numbered 0 to 15 as the user drew them on the deck**: top rows first, left cluster 0 to 3, right cluster 4 to 7, then the bottom rows, left 8 to 11, right 12 to 15 (`PAD_CELLS` in `surface.js`; the assignment panel shows `PAD n` 0-based). The note->index map is unchanged (chromatic base 24).
- **Nothing drives an effect by default, ever.** `defaultKnobs()` is eight nulls; templates carry no `fx:*` or `engine:intensity` knobs (the factory presets keep hue / fade length / kit level; the authored templates map nothing). The router reconciles fx every frame (`reconcileFx`): a key no assignment drives any more resets to its rack default, and a rack a control switched on switches off again when nothing drives it. Clearing a pad / knob / route therefore also stops whatever effect it drove.
- **Nothing auto-rotates, in any scene or effect** (hard rule 8 in [docs/SCENE_CONTRACT.md](docs/SCENE_CONTRACT.md)). Hand-driven orbits, per-particle flow, scrolling, breathing, path travel and noise-domain flows stay. Forward motion only in flight scenes; hyperspace as a layer above the scene.
- **Every shader is GLSL3** (`glslVersion: THREE.GLSL3`, `in` / `out`, `out vec4 fragColor`, `texture()`); `onBeforeCompile` injections into three's built-in materials keep three's conventions by necessity. Keep the stack current (three 0.185.1, Electron 43.4.1, esbuild 0.28.2, target chrome140).
- **No AI attribution anywhere**: no `Co-Authored-By` trailers, no "generated by" lines in headers, docs, or PR bodies. Commit messages are plain.
- **Scenes that read raw knobs say so in the SCENE_CONTRACT inventory**: Beam Sixteen KNOB 4; Nature's Tomb KNOB 5 (development, plus any strike), KNOB 6 (organism), KNOB 7 (species); Miracle Mile KNOB 5 (yield) and KNOB 6 (act). Those are the no-assignment fallback only, **a scene's events and parameters are declared in `meta.controls` and implemented as `action()` / `setParam()`** so they bind to any control through the assignment UI (SCENE_CONTRACT, "The scene control surface"). New scene work declares its surface.
- **Scenes open on the show.** A scene whose brief has an opening element holds dark until the show starts (the first beat the analyser hears, the transport playing, or any pad) and then plays that element (Will I Dream the big bang, Miracle Mile the collider, Nature's Tomb the replicating molecule). Dark, not dead: something faint breathes with the level.
- **Nothing appears at its size.** A body, an object, a form that comes into existence grows from a point (or its seed) into its size, never a pop-in at full scale (user rule, 2026-08-21, from Will I Dream's arrivals; applied there with a 1.6 s ease-out, and it binds every scene).
- **A scene is never drawn until the warm pipeline has built, linked and drawn it once** (ENGINE, "The warm pipeline"); a switch to a cold scene defers rather than stalls. Do not reintroduce a synchronous `renderer.compile` + first draw into a live frame, and keep `ctx.environment` a lazy getter.
- **`voxels.js` is the user's favourite scene and is off-limits** unless they say otherwise (the one-term orbit removal was the only edit, forced by the "any scene" rule).
- **Apache-2.0 ports** (`ferrofluid`, `chladni`, `valley` (theDAW's cymatics shaders) carry the licence notice and statement of changes in their headers; do not strip them. **VJ-9000 has no licence file upstream** (`vjshader`, `spectra`, the fx rack derive from it); add one before third-party distribution. **Audima's terms forbid redistributing their binaries**) the Doctor fetches from `cdn.audima.com.au` onto the user's machine and never bundles. **theDAW alignment**: the synth keeps theDAW's `voiceTrigger` signature and `controlManifest` shape; audio modules are factory functions taking `ctx` and a destination array.
- **UI naming**: no element titled twice, no juvenile wording, no AI-UI tropes; terse instrument labels; the sci-fi cockpit aesthetic from the user's `ScifiUI` packs (the user's memory note `user-naming-constraints` has the full rule).
- **Keep headless app launches rare**: iterate with the scene harness, batch app checks into one probe per pass, reserve screenshots for milestones. The user runs the installed build while work happens; their persisted `settings.layout` is theirs, a dev run restoring collapsed rails is the feature working, not a regression.

## 4. Verifying without a human

No test suite. Two tools:

- **The scene harness** (`node scripts/scene-harness.js plan.json`): compile + render + stills in a hidden Electron window. Use it for any scene work; it does not touch the app, the settings, or the hardware. A shot's `io` patch takes `actions` / `params` (the scene control surface), `strikes` (several pads at once), `transport`; the report's `msPerFrame` is closed by a pipeline-draining `readPixels` and `gpuMs` is the timer query where the driver exposes it (`null` on this machine's ANGLE/D3D11), the old `gl.finish()` number was fiction on this driver. Absolute GPU timings on this laptop vary up to 2× under sustained load (the GPU downclocks); compare within a run, and do not measure while another harness or the app is rendering.
- **The app, headlessly**, through env vars read in `src/main/main.js` ([docs/ENVIRONMENT.md](docs/ENVIRONMENT.md) has the reference and working probe examples): `SWAYCOMMAND_SHOT` (capture to PNG, then quit), `SWAYCOMMAND_SHOT_DELAY` (ms, default 5000, must exceed the probe's own timers), `SWAYCOMMAND_WINDOW` (`WxH`), `SWAYCOMMAND_AUTOPLAY` (template id or `.sway` path; skips the SYSTEM modal), `SWAYCOMMAND_SCENE` (force a scene id, never use it to judge discoverability), `SWAYCOMMAND_PROBE` (JS evaluated 3000 ms after load; an async IIFE returning a promise is awaited; the result prints as `[probe] ...`). `window.__swaycommand` is the automation handle: `{ state, studio, openStudio(tab), openDocs, renderPads, renderSamples, transport, projectStore, router, selectControl, openProject, saveProject }`; `state.engine` / `state.midi.control` drive scenes and fake strikes (`control.pads[i] = 1` is one strike; `control.knobs[i]`, `control.gestures.*`, `control.xy`); `state.engine.stats` carries `worst` / `slow` / `stallLog` / `warm` for frame health; `state.engine.sceneAction(id, key)` / `setSceneParam(id, key, v)` reach a scene's control surface. **To reproduce anything cold-cache (first-launch behaviour), pass `--user-data-dir=<fresh dir>` to `electron .`**, the default profile's GPUCache hides it. Launch: `node scripts/build-renderer.js`, then `npx electron .` with the env set (or `npm start`). The packaged exe can be launched the same way and its stdout redirected. `scripts/midi-session.ps1` is the prepared hardware session.

Standing traps: `ELECTRON_RUN_AS_NODE` may be set in agent shells (Electron then starts as Node and dies on `whenReady`), clear it every launch; env vars leak between runs (clear `SWAYCOMMAND_AUTOPLAY` / `SWAYCOMMAND_SCENE`); the hardware may be live (a scene changing "by itself" mid-probe is usually a real strike on a template-assigned pad); do not read the WebGL canvas by drawing it into a 2D canvas (no `preserveDrawingBuffer`, it reads black); the Bash tool's command length limit (write large files with the file tools); **a stale headless instance steals the Sway**, Windows lets one process hold a MIDI input, and on 2026-08-21 a dev instance (`electron .`, started 00:34, never quit) sat on the port for hours so the installed app read KEYS on every scene ("the Sway is not working on ANY scene" was a zombie process, not code): before blaming the MIDI path run `tasklist | findstr electron` (and `SwayCommand`), kill the stray tree (`taskkill /PID <pid> /T /F`; from Git Bash `MSYS_NO_PATHCONV=1 cmd /c "taskkill /PID <pid> /T /F"`), relaunch, and make every headless launch end (`SWAYCOMMAND_SHOT` quits it; check `tasklist` after any run that errored). Since then `midi.js` opens each bound input explicitly: a failed open shows **BUSY** on the link pill and a `PORT BUSY ...` line in the MIDI monitor (K).
